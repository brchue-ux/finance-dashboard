*Decisions that were ambiguous or wrong, now with a concrete recommended direction:*
- **Auth mechanism** — should be `@better-auth/expo` (server) + `@better-auth/expo/client` (client, `expoClient({scheme, storage: SecureStore})`), not raw Bearer and not plain cookies. This is Better Auth's own first-party answer for "one backend, Expo web + native," confirmed via current docs.
- **LLM streaming contract** — `backend/package.json` pins `ai@^4.0.0` (actually installed: 4.3.19); spec claims "v7" in four places including a Node-22 deployment checklist step. That upgrade was never done — only documented. Frontend hand-parses the raw v4 wire format with zero `@ai-sdk/react` client. Either commit to v4 explicitly (drop the v7/Node-22 claims until a real upgrade happens) or upgrade both ends together using the SDK's own client stream helpers instead of hand-parsed bytes.
- **Plaid Link integration mechanism** — official native SDK requires a custom EAS dev client (incompatible with Expo Go); never decided or accounted for anywhere. **Locked 2026-07-18, corrected same day:** raw WebView (the original recommendation here) is Plaid's own deprecated integration path. Real mechanism: **Plaid Hosted Link** (`hosted_link_url` from `/link/token/create`, opened via `ASWebAuthenticationSession`/Custom Tabs — exactly what `expo-web-browser`'s `openAuthSessionAsync` wraps) — achieves the same goal (no native SDK, no custom EAS dev client) via Plaid's current sanctioned path instead of a deprecated one. SnapTrade's browser-based hosted-portal flow is unaffected. See `.claude/wayfinder/remediation-decisions-2026-07-18.md` for the full decision record and the still-open two-redirect-URI wrinkle (`completion_redirect_uri` vs `redirect_uri`).
- **SnapTrade connection redirect** — `loginSnapTradeUser()` supports a `customRedirect` param; `/api/snaptrade/connect` never sets it. Without it, a user finishing the Wealthsimple OAuth flow lands on a SnapTrade default page, not back in the app. Same class of bug as the Plaid `redirect_uri` issue already fixed this session.
- **Holding Detail chart rendering on native** — ticket 006's "mobile rendering" decision literally describes Next.js SSR (`dynamic(..., {ssr:false})`), written against a frontend framework this project doesn't use (Expo, not Next.js — decided in a different, non-cross-referenced ticket). Lightweight Charts has no RN renderer; real answer is a `react-native-webview` wrapper with injected-JS data passing. Worth keeping (preserves the deepentropy 446-indicator feature set) but needs to be an explicit, specified decision, not an inherited assumption.
- **Google Sheets historical import** — completely unbuilt (schema only, dead Settings button). Given it's a true one-time, single-user, admin-time action, recommend a `scripts/import-sheets.ts` CLI script (same pattern as `db/seed.ts`) instead of building a third in-app OAuth-redirect flow for something that runs exactly once, ever.
