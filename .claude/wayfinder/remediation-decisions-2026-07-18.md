## Ticket 010 — LLM tool use (web search + technical indicators)

**Status: LOCKED — fully.**

Root problem this closes: spec §8 claims web search and `twelvedata/mcp` are "enabled," but `lib/llm/advisory.ts`'s `generateText`/`streamText` calls pass no `tools:` parameter at all today — zero tool access currently exists in code.

1. **Web search:** `@ai-sdk/anthropic@4` exposes this natively as a provider-executed tool — `anthropic.tools.webSearch_20260209()` (confirmed present in the installed package's type defs; there's an older `webSearch_20250305` too, use the current dated version). Provider-executed means Anthropic's own servers do the actual searching, billed through the same Anthropic API call — no separate search API, no extra infrastructure, no second vendor.
2. **Technical indicators (`twelvedata/mcp`): self-hosted, not the vendor's remote endpoint.** Original spec text ("No separate Railway service required — it runs as a remote MCP endpoint," i.e. `mcp.twelvedata.com`) was a simplicity/convenience choice, not a considered reliability decision — confirmed via research this session: the underlying Twelve Data data API has a genuine 99.95% uptime SLA and long track record, but Twelve Data's *own hosting of the MCP wrapper layer* has no separately published reliability history — it's newer, less-proven infrastructure sitting on top of a proven API. `twelvedata/mcp` is open source and self-hostable (Dockerfile provided, Python 3.10+, uses your own Twelve Data API key) at the same cost (still free-tier eligible — confirmed directly against Twelve Data's own pricing page that the free Basic plan includes 100+ technical indicators, correcting an initial wrong secondhand claim that said otherwise). Polygon.io was checked as the alternative "pay for reliability" vendor and rejected: not actually cheaper ($79/mo for production-grade data vs. $0), and only covers 4 core indicators vs. Twelve Data's 100+. **Decision: run `twelvedata/mcp` as a second, self-hosted Railway service** (it's Python-based, so a separate deployable service from the Next.js backend, not something that runs inside the same Node process), using the project's own `TWELVE_DATA_API_KEY`. Removes dependency on the vendor's own unproven hosting while keeping the same data, same cost, same indicator breadth.
3. **MCP client connection: persistent, module-level, not per-request.** Matches this backend's actual deployment model (persistent Railway Node process, not serverless) — connect once at module load, reuse across requests, avoid paying a connection handshake on every advisory call.
4. **Graceful degradation, precisely defined (not "fall back to web search"):** web search and MCP-sourced indicator data are NOT substitutes for each other — MCP is the sole source of precise, computed indicator numbers (RSI, MACD, moving averages); web search is a separate tool for a separate purpose (news, macro context, ticker headlines) and stays available regardless of MCP's status. If the self-hosted MCP service is unreachable, its tools are simply omitted from that call's `tools:` list — Claude never sees them as an option — and the system prompt gets an explicit instruction (same pattern as the existing Tangerine-staleness note) not to estimate or fabricate specific indicator values from web search or any other source when MCP tools aren't available. The goal ("data displayed exactly the same for the user") is met by never producing an approximated number, not by disguising a fallback to look identical to the real thing.
5. **Rate limits to design around, not just accept:** free tier is 800 credits/day *and* 8 calls/minute. The per-minute cap is the more realistic risk given an LLM autonomously deciding when to call the tool (could plausibly check several holdings' indicators in quick succession within one advisory session). Needs an app-level conservative cap on indicator lookups per session so it never approaches 8/minute — specific number to set during implementation, not decided here.

6. **Tool availability scope: both tools, both paths — auto-cards AND chat, unrestricted, for now.** Explicit user decision: prioritize UX/analysis quality over minimizing API call volume at this stage. Auto-generated cards and interactive chat both get full access to web search and the self-hosted indicator MCP — no asymmetric restriction, even though this means more calls, more exposure to the 8-calls-per-minute rate limit, and a higher (currently unestimated) cost than the original ~$1-3/month figure, which was computed with zero tool use. Accepted deliberately, not overlooked.

**Deferred, not decided — must be revisited before launch:** whether to taper back auto-card call frequency/tool access (e.g., restrict to MCP-only on auto-cards, or add a stricter per-session cap) *or* pay for a higher Twelve Data tier to raise the rate-limit ceiling, once real usage patterns from actual use are known rather than guessed at now. This is the same shape of decision as the existing Post-Launch Review Items already in spec §11 (Scotiabank relink-frequency KPI, Tangerine sync reliability review) — should be added there as its own item during the culmination pass: "Review LLM tool-call volume and cost after N weeks of real usage; decide between tapering auto-card tool access or upgrading the Twelve Data plan."

## Tickets 008/004 — Historical spreadsheet import (Google Sheets + Excel)

**Status: LOCKED.**

Root problem this closes: completely unbuilt — `import_jobs` table exists in schema, nothing else does. `settings.tsx`'s "Import historical data" button has no `onPress` handler.

**Superseded along the way, recorded so it isn't accidentally revived:** the first proposal in this walkthrough was a one-time, developer-run CLI script (mirroring `db/seed.ts`), reasoning it was a single admin-time action. User correction: at any real scale this is a **per-user onboarding feature** — anyone migrating off Excel/Sheets does this at their own signup time, indefinitely into the future. A CLI script doesn't serve that at all. Fully retired in favor of the below.

1. **Three parallel, user-selectable import paths — not one:**
   - **CSV upload.** Works identically for a Google Sheets or Excel export (both tools natively support "export to CSV"), no OAuth, no vendor-specific integration. Lowest cost, covers anyone who doesn't mind exporting before uploading.
   - **Google Sheets live connection.** Sheets API + OAuth. Two known risks to design around, not just accept: the `googleapis` auto-refresh bug (googleapis/google-api-nodejs-client#2350 — must explicitly set `expiry_date` in `setCredentials`, auto-refresh doesn't reliably trigger without it) and the OAuth consent-screen "Testing" status trap (refresh tokens revoked after 7 days unless the consent screen is Published or the user is added to a test-user allowlist).
   - **Excel live connection.** Microsoft Graph API (Excel workbook endpoints) + Microsoft identity platform OAuth. Verified real and current (2026 docs) via direct research, not assumed. Two things specific to this path: (a) OneDrive change-notification subscriptions are folder-level, not file-level — the app has to subscribe to the containing folder and filter for the specific file on each notification; (b) subscriptions expire and need periodic renewal, Microsoft's own analog to a refresh-token lifecycle, not a cleaner alternative to Google's.
   - **Explicitly accepted trade:** this is two full, independent vendor OAuth integrations plus CSV, not one generic "spreadsheet" abstraction — a real scope increase over the original one-mechanism plan, taken on deliberately because manual re-export on every edit is unacceptable friction for someone actively using their spreadsheet as an ongoing source of truth (not just a one-time migration dump).
2. **Why CSV was kept as a first-class option rather than replaced by the live connections:** covers both Google Sheets and Excel with a single mechanism and zero OAuth trust/consent friction — good for someone doing a one-time historical dump who doesn't want to grant either vendor's app access to their account at all. Live connections are for the person who wants ongoing, low-friction updates without manual re-export. Both are real, legitimate use cases, not a compromise.
3. **Dedup for repeated CSV uploads:** fingerprint each row (date + description + amount) and skip anything matching an already-imported transaction, since re-exports realistically contain the full history each time, not just new rows, and there's no stable external ID the way Plaid's `plaidTransactionId` provides.
4. **Schema check performed, not assumed:** `transactions.plaidTransactionId` is already nullable — CSV/spreadsheet-sourced rows can coexist in the same table as Plaid-sourced ones with no migration needed there. But `transactions.accountId` is `NOT NULL`, referencing `bank_accounts` — a user with zero linked banks (spreadsheet-only persona) has nowhere to attach imported transactions today. **Needs a new `bank_accounts.type` value** (e.g. `"manual"`) representing the spreadsheet/CSV source itself; created automatically on first import so the rest of the app (transaction feed, budget math, category engine, Settings' connected-accounts list) works identically regardless of data source.
5. **Not yet decided — implementation detail, not a blocking decision:** exact `import_jobs.source` values to add (currently schema comment says `"google_sheets" | "csv"` — needs a distinct value for the Excel path too) and the actual Settings UI for choosing between the three paths (a picker/menu of some kind, not a single button — not yet designed).

## Contract-gap items 3 + 4 + 5 — Native alert engine, unified alerts feed, mark-as-read

**Status: LOCKED (confirmed by user 2026-07-18 — "I'm good with everything on Dead Dependency number one... I agree with Dead Dependency number two... I agree with the remaining points... I agree with the cluster proposal").**

Root problems this closes: the alert engine was schema-only (nothing writes `alert_fires`), `/api/alerts` reads the raw `tradingview_alerts` webhook log instead of the spec's unified feed, the TradingView webhook hardcodes `userId: "DEFAULT_USER"`, and no mark-as-read exists.

1. **Two of spec §5.6's load-bearing dependencies are dead — verified directly, not assumed:**
   - `yahoo-finance2.quoteCombine()` **does not exist** in the installed package (v2.14.0) — no module, no export, no type def; only a dangling README link. Never needed anyway: plain `quote()` accepts `string[]` and batches all tickers into one HTTP request (verified live), and the poller collects all distinct tickers itself in one place. `quoteCombine` was a debounce wrapper for scattered single-ticker calls — a problem this design doesn't have.
   - `@sebspark/trading-hours` **cannot do this job**: pulled the actual package (v1.0.9) — the API is `isOpen(mic)` (the spec's `isTradingTime()` doesn't exist), and it covers only 13 **European** markets (SEB/Swedish-bank origin). No NYSE, no NASDAQ, no TSX. Dropped entirely, replaced by nothing (see 2).
2. **Market-hours gate: per-symbol `marketState` from Yahoo's own quote response** (`"REGULAR" | "CLOSED" | "PRE" | "POST" | …` — already in the data being fetched, zero added dependencies). Only evaluate an alert when its own symbol's market is open (`REGULAR`, or `PRE`/`POST` when `extendedHours = 1` — schema already supports this). Strictly more correct than any calendar package: per-symbol (handles NYSE-open/TSX-closed divergent holidays), handles half-days, and closes a real false-refire bug the spec design had (recurring `pct_change` alert with cooldown re-firing on a holiday against the prior session's stale change figure). **Verified live with one batched call spanning NasdaqGS (AAPL), NYSE (IBM), Toronto (RY.TO), S&P 500 (`^GSPC`), and NASDAQ Composite (`^IXIC`)** — every venue returns its own `marketState`; index symbols are alertable too. A simple Mon–Fri / ~4:00–20:00 ET window remains as the cheap outer skip on the cron — cost optimization only, not the correctness mechanism.
3. **`yahoo-finance2` version pin — fixes a broken-at-runtime bug, not just the poller:** installed v2.14.0 is a gutted transitional release: only `quote` + `autoc` modules, default export is a class that existing code never instantiates, and **`chart()` doesn't exist in it** — yet `lib/market-data/yahoo.ts` calls `yahooFinance.chart(...)`. The existing OHLCV path is broken at runtime against the installed version; almost certainly the true root of the "pre-existing TypeScript errors in yahoo.ts" open item. **Pin `yahoo-finance2@3.x` (3.15.4 current, 2026-07-01)** — full module set, batch `quote(string[])`, `marketState`, `chart()` all confirmed present in its type defs and via live call. API change: `new YahooFinance()`, one shared instance between poller and OHLCV route. v4.0.0 (released 2026-07-11, one week old) deliberately not chosen — add "review yahoo-finance2 v4" as a post-launch review item at culmination.
4. **Engine mechanics (per spec §5.6, kept where still sound):** in-process `node-cron` (v4.6.0 — verified current/maintained) in the persistent Railway Node process, registered once via Next.js `instrumentation.ts` `register()` (the sanctioned once-per-server-start hook); 5-min cycle; mutex against overlapping cycles; `price_cache` last-known-good writes; one-time-fire default with optional `cooldown_seconds`; `firedAtBucket` DB-level dedup — all unchanged.
5. **Unified feed delivered at the API layer, not the table layer.** The recorded FK issue is actually three blockers: `alert_fires.alertId`, `.threshold`, and `.triggerPrice` are all NOT NULL and all impossible for a TradingView webhook row (no standing alert, no numeric threshold, optional price). Nullable-ifying them would gut real native-path rigor AND silently break dedup (SQLite unique indexes treat NULLs as distinct — `(alertId, firedAtBucket)` stops deduplicating). Instead: `alert_fires` stays native-only with constraints intact; `/api/alerts` queries `alert_fires` + `tradingview_alerts` and normalizes both into one response shape (`id, source, ticker, condition label, price, timestamp, severity, unread, analyzedAt`). TradingView needs no DB dedup — each webhook is one event and the raw log is the record. `alert_fires.source` column kept even though now always `"native"` (dropping = migration for zero benefit; leaves the door open). Spec §5.6's "unified UI queries `alert_fires`" sentence gets corrected at culmination.
6. **Mark-as-read:** add `readAt` to `tradingview_alerts` — its existing `analyzedAt` is a different fact (ran LLM analysis ≠ saw the alert; current UI conflates them). One endpoint (`PATCH /api/alerts/:id/read` shape) routing to the right table by the item's `source`.
7. **`DEFAULT_USER` fix: per-user hashed webhook secret stored in the DB** — the secret itself is the user identity (exactly what the code's own multi-user comment envisioned). Kills the `TRADINGVIEW_WEBHOOK_SECRET` env var; handler hashes the incoming plaintext and looks up the owning user. Single user = one seeded row; multi-user needs zero redesign.
8. **Frontend:** `useAlerts`/`AlertCard`/`alerts.tsx` currently typed to the raw TradingView row shape — re-typed to the normalized feed shape at implementation.
9. **Implementation-time notes (recorded, not decided):** whether an alert whose condition is already true at creation fires on first poll or requires a crossing; job-level noise control for poll-cycle logging; exact normalized-shape field names.

## New feature — Observability: statistics, system status, developer logs

**Status: LOCKED (confirmed by user 2026-07-18).** User-originated request ("there definitely needs to be a developer one, like logs, just for debugging"), shaped by the finding that current observability is nearly zero: two `lastSyncedAt` timestamps, `import_jobs` (imports only), and `console.log` to Railway stdout (ephemeral, outside the app's reach) — a developer screen built today would have nothing to display.

1. **Structural piece: new `job_runs` table.** Every background execution writes a row: job type (`plaid_sync`, `snaptrade_sync`, `alert_poll`, `nightly_batch`, `import`, `tradingview_webhook`), status, started/finished timestamps, error message, metadata JSON for counts (tickers polled, alerts fired, transactions synced, tokens used, etc.). Same shape as the existing `import_jobs` pattern, generalized. **Governing rule, explicit user instruction: capture every data point available at each job run — trim later, can't backfill.** Volume is a non-issue (~80 tiny rows/day from alert polling); pruning policy is an implementation detail, decided later.
